# Verify Journal and Crisis Plan in production

Last reviewed: 2026-09-06

Run this after the Journal/Crisis Plan production deployment and before declaring the release fully
verified. Use only synthetic accounts and non-sensitive plan text. Keep command output that contains
identifiers local; release evidence should contain only timestamps, AWS event IDs, resource aliases,
counts, and pass/fail outcomes.

## 1. Set the release values and discover resources

```console
export AWS_PROFILE=naaseh-admin
export AWS_REGION=us-west-2
export PROD_STACK=NaasehProd
export RELEASE_RUN_ID=REPLACE_WITH_GITHUB_RUN_ID
export VERIFY_STARTED_AT="$(date -u '+%Y-%m-%dT%H:%M:%SZ')"

aws sso login --profile "$AWS_PROFILE"
aws sts get-caller-identity --profile "$AWS_PROFILE"
gh run view "$RELEASE_RUN_ID" --json conclusion,headSha,url,jobs \
  --jq '{conclusion,headSha,url,jobs:[.jobs[]|{name,conclusion}]}'

aws cloudformation list-stack-resources \
  --profile "$AWS_PROFILE" --region "$AWS_REGION" --stack-name "$PROD_STACK" \
  --output json > /tmp/naaseh-prod-resources.json

TABLE_NAME="$(jq -r '.StackResourceSummaries[] | select(.ResourceType=="AWS::DynamoDB::Table" and (.LogicalResourceId|startswith("Data"))) | .PhysicalResourceId' /tmp/naaseh-prod-resources.json)"
SHARING_KEY_ID="$(jq -r '.StackResourceSummaries[] | select(.ResourceType=="AWS::KMS::Key" and (.LogicalResourceId|startswith("CrisisPlanSharingKey"))) | .PhysicalResourceId' /tmp/naaseh-prod-resources.json)"
BROKER_FUNCTION="$(jq -r '.StackResourceSummaries[] | select(.ResourceType=="AWS::Lambda::Function" and (.LogicalResourceId|startswith("CrisisPlanBrokerFunction"))) | .PhysicalResourceId' /tmp/naaseh-prod-resources.json)"
CRISIS_FUNCTION="$(jq -r '.StackResourceSummaries[] | select(.ResourceType=="AWS::Lambda::Function" and (.LogicalResourceId|startswith("CrisisPlanFunction"))) | .PhysicalResourceId' /tmp/naaseh-prod-resources.json)"
API_LOG_GROUP="$(jq -r '.StackResourceSummaries[] | select(.ResourceType=="AWS::Logs::LogGroup" and (.LogicalResourceId|startswith("SyncLogs"))) | .PhysicalResourceId' /tmp/naaseh-prod-resources.json)"
BROKER_LOG_GROUP="$(jq -r '.StackResourceSummaries[] | select(.ResourceType=="AWS::Logs::LogGroup" and (.LogicalResourceId|startswith("CrisisPlanBrokerLogs"))) | .PhysicalResourceId' /tmp/naaseh-prod-resources.json)"
BACKUP_VAULT="$(jq -r '.StackResourceSummaries[] | select(.ResourceType=="AWS::Backup::BackupVault") | .PhysicalResourceId' /tmp/naaseh-prod-resources.json)"
BACKUP_PLAN_ID="$(jq -r '.StackResourceSummaries[] | select(.ResourceType=="AWS::Backup::BackupPlan") | .PhysicalResourceId' /tmp/naaseh-prod-resources.json)"

printf 'table=%s\nkey=%s\nbroker=%s\napi=%s\napi-log=%s\nbroker-log=%s\nvault=%s\nbackup-plan=%s\n' \
  "$TABLE_NAME" "$SHARING_KEY_ID" "$BROKER_FUNCTION" "$CRISIS_FUNCTION" \
  "$API_LOG_GROUP" "$BROKER_LOG_GROUP" "$BACKUP_VAULT" "$BACKUP_PLAN_ID"
```

Each value must be exactly one non-empty line. Stop if identity is root, the workflow conclusion is
not `success`, or its `validate`, `deploy`, or `smoke` job did not succeed. The smoke job is the
evidence for both API routes, two separate durable reads, the signed sharing-key registry,
concealed broker denial, and `Cache-Control: no-store`.

## 2. Exercise sharing and revocation

This portion uses the browser because client-side Journal keys must never be placed in a shell.

1. Sign in as a temporary synthetic owner, enroll Journal through the application if necessary,
   and create a Crisis Plan containing only clearly synthetic text.
2. Share it with a temporary synthetic ordinary recipient selected in the application.
3. In a separate browser profile, sign in as the recipient and open the shared plan online. Confirm
   it is read-only. Then go offline and confirm no readable recipient copy remains.
4. As the owner, revoke the recipient. Confirm the recipient disappears from the active share list.
5. As the recipient, confirm the shared-list view, direct-open route, and broker-assisted open all
   deny access. Do not bypass the UI or insert DynamoDB records manually.

Record the UTC start/end times and safe correlation/event IDs. Do not record either account's ID,
the plan ID, content, ciphertext, wraps, grants, cookies, or request bodies.

## 3. Verify the real KMS boundary

Resolve the broker execution role and sharing-key ARN:

```console
BROKER_ROLE_ARN="$(aws lambda get-function-configuration \
  --profile "$AWS_PROFILE" --region "$AWS_REGION" --function-name "$BROKER_FUNCTION" \
  --query Role --output text)"
SHARING_KEY_ARN="$(aws kms describe-key \
  --profile "$AWS_PROFILE" --region "$AWS_REGION" --key-id "$SHARING_KEY_ID" \
  --query KeyMetadata.Arn --output text)"
printf 'broker-role=%s\nsharing-key=%s\n' "$BROKER_ROLE_ARN" "$SHARING_KEY_ARN"
```

Find the successful decrypt generated by step 2 and inspect only safe fields:

```console
aws cloudtrail lookup-events \
  --profile "$AWS_PROFILE" --region "$AWS_REGION" \
  --lookup-attributes AttributeKey=EventName,AttributeValue=Decrypt \
  --start-time "$VERIFY_STARTED_AT" --max-results 50 --output json \
| jq --arg role "${BROKER_ROLE_ARN##*/}" '
  [.Events[].CloudTrailEvent | fromjson
   | select((.userIdentity.arn // .userIdentity.principalId // "") | contains($role))
   | {eventTime,eventID,actor:(.userIdentity.arn // .userIdentity.principalId),eventSource,eventName,errorCode}]'
```

There must be a successful `kms.amazonaws.com` `Decrypt` event for the broker role. Do not print
`requestParameters` because it can contain ciphertext.

Now simulate every Lambda role. The broker must be `allowed`; all other production Lambda roles
must be `implicitDeny` or `explicitDeny`:

```console
aws iam simulate-principal-policy \
  --profile "$AWS_PROFILE" --policy-source-arn "$BROKER_ROLE_ARN" \
  --action-names kms:Decrypt --resource-arns "$SHARING_KEY_ARN" \
  --query 'EvaluationResults[0].EvalDecision' --output text

jq -r '.StackResourceSummaries[] | select(.ResourceType=="AWS::IAM::Role") | .PhysicalResourceId' \
  /tmp/naaseh-prod-resources.json \
| while IFS= read -r role_name; do
    role_arn="arn:aws:iam::093733938983:role/$role_name"
    test "$role_arn" = "$BROKER_ROLE_ARN" && continue
    decision="$(aws iam simulate-principal-policy --profile "$AWS_PROFILE" \
      --policy-source-arn "$role_arn" --action-names kms:Decrypt \
      --resource-arns "$SHARING_KEY_ARN" \
      --query 'EvaluationResults[0].EvalDecision' --output text)"
    printf '%s %s\n' "$role_name" "$decision"
  done
```

Stop if any non-broker role is allowed.

## 4. Check only the necessary alarms and content-free logs

The release adds no dedicated alarm resources. It reuses three existing alarms:

- `SecuritySignalAlarm`: `CrisisPlanKmsFailure >= 1` or ten broker denials in five minutes;
- `OperationalFailureSignalAlarm`: `CrisisPlanOperationFailure >= 1`; and
- `RestoreWorkflowFailureAlarm`: failed, timed-out, or aborted restore validation.

Expected isolated denials do not alarm individually. Conflict and rotation-required metrics remain
dashboard signals because they are normal user-resolvable states.

```console
aws cloudwatch describe-alarms \
  --profile "$AWS_PROFILE" --region "$AWS_REGION" \
  --alarm-name-prefix "$PROD_STACK" \
  --query 'MetricAlarms[?contains(AlarmName, `SecuritySignalAlarm`) || contains(AlarmName, `OperationalFailureSignalAlarm`) || contains(AlarmName, `RestoreWorkflowFailureAlarm`)].{Name:AlarmName,State:StateValue,Reason:StateReason}'

for log_group in "$API_LOG_GROUP" "$BROKER_LOG_GROUP"; do
  aws logs tail "$log_group" \
    --profile "$AWS_PROFILE" --region "$AWS_REGION" --since 30m --format short
done
```

All three alarms must be `OK`. Investigate `ALARM`, unexpected denial volume, Lambda errors, KMS
failures, or messages containing protected content. Do not paste log bodies into release evidence.

## 5. Verify PITR, backup selection, Vault Lock, and a recovery point

```console
aws dynamodb describe-continuous-backups \
  --profile "$AWS_PROFILE" --region "$AWS_REGION" --table-name "$TABLE_NAME" \
  --query 'ContinuousBackupsDescription.PointInTimeRecoveryDescription.{Status:PointInTimeRecoveryStatus,Earliest:EarliestRestorableDateTime,Latest:LatestRestorableDateTime}'

TABLE_ARN="$(aws dynamodb describe-table \
  --profile "$AWS_PROFILE" --region "$AWS_REGION" --table-name "$TABLE_NAME" \
  --query Table.TableArn --output text)"
while IFS= read -r selection_id; do
  aws backup get-backup-selection \
    --profile "$AWS_PROFILE" --region "$AWS_REGION" \
    --backup-plan-id "$BACKUP_PLAN_ID" --selection-id "$selection_id" \
    --query 'BackupSelection.{Resources:Resources,NotResources:NotResources}'
done < <(aws backup list-backup-selections \
  --profile "$AWS_PROFILE" --region "$AWS_REGION" --backup-plan-id "$BACKUP_PLAN_ID" \
  --output json | jq -r '.BackupSelectionsList[].SelectionId')

aws backup list-backup-vaults \
  --profile "$AWS_PROFILE" --region "$AWS_REGION" \
  --query "BackupVaultList[?BackupVaultName=='${BACKUP_VAULT}'].{Name:BackupVaultName,Locked:Locked,MinRetentionDays:MinRetentionDays,MaxRetentionDays:MaxRetentionDays,LockDate:LockDate,RecoveryPoints:NumberOfRecoveryPoints}"

aws backup list-recovery-points-by-backup-vault \
  --profile "$AWS_PROFILE" --region "$AWS_REGION" \
  --backup-vault-name "$BACKUP_VAULT" \
  --query 'RecoveryPoints[?Status==`COMPLETED`].{Created:CreationDate,Type:ResourceType,Arn:RecoveryPointArn}'
```

PITR must be enabled. The selection must cover `TABLE_ARN`. The vault result must have
`Locked: true`, the approved retention range, and at least one current completed DynamoDB recovery
point.

Use `list-backup-vaults` for this check. In this account, IAM policy simulation permits
`backup:DescribeBackupVault`, but the live `describe-backup-vault` call returns AWS Backup's
`Insufficient privileges`; that does not prove the role lacks the IAM action. `list-backup-vaults`
returns the authoritative Vault Lock fields needed here, so no additional IAM grant is required.

## 6. Run the isolated restore test

AWS Backup Restore Testing is schedule-driven; a manual `start-restore-job` is not equivalent and
will not exercise the approved validation workflow. The normal plan runs quarterly. First inspect
its schedule and recent jobs:

```console
export RESTORE_PLAN=NaasehQuarterlyRestoreTest
aws backup get-restore-testing-plan \
  --profile "$AWS_PROFILE" --region "$AWS_REGION" \
  --restore-testing-plan-name "$RESTORE_PLAN"

RESTORE_PLAN_ARN="$(aws backup get-restore-testing-plan \
  --profile "$AWS_PROFILE" --region "$AWS_REGION" \
  --restore-testing-plan-name "$RESTORE_PLAN" \
  --query RestoreTestingPlan.RestoreTestingPlanArn --output text)"
aws backup list-restore-jobs \
  --profile "$AWS_PROFILE" --region "$AWS_REGION" \
  --by-restore-testing-plan-arn "$RESTORE_PLAN_ARN" \
  --query 'RestoreJobs[].{Created:CreationDate,Type:ResourceType,Status:Status,Validation:ValidationStatus,Deletion:DeletionStatus,Id:RestoreJobId}'
```

If a completed, current feature-release execution already exists, do not create another. Otherwise,
schedule one bounded near-term execution by temporarily moving the CDK-managed plan schedule, then
restore the exact original configuration as soon as AWS creates the restore jobs:

```console
aws backup get-restore-testing-plan \
  --profile "$AWS_PROFILE" --region "$AWS_REGION" \
  --restore-testing-plan-name "$RESTORE_PLAN" --output json \
  > /tmp/naaseh-restore-plan-original.json

FEATURE_CRON="cron($(date -u -v+20M '+%M %H %d %m ? %Y'))"
jq --arg schedule "$FEATURE_CRON" '{
  RestoreTestingPlanName:.RestoreTestingPlan.RestoreTestingPlanName,
  RestoreTestingPlan:{
    RecoveryPointSelection:.RestoreTestingPlan.RecoveryPointSelection,
    ScheduleExpression:$schedule,
    ScheduleExpressionTimezone:(.RestoreTestingPlan.ScheduleExpressionTimezone // "Etc/UTC"),
    StartWindowHours:.RestoreTestingPlan.StartWindowHours
  }
}' /tmp/naaseh-restore-plan-original.json > /tmp/naaseh-restore-plan-once.json

aws backup update-restore-testing-plan \
  --profile "$AWS_PROFILE" --region "$AWS_REGION" \
  --cli-input-json file:///tmp/naaseh-restore-plan-once.json
```

Poll no more often than every five minutes until the DynamoDB and S3 jobs appear. Then immediately
restore the CDK schedule:

```console
jq '{
  RestoreTestingPlanName:.RestoreTestingPlan.RestoreTestingPlanName,
  RestoreTestingPlan:{
    RecoveryPointSelection:.RestoreTestingPlan.RecoveryPointSelection,
    ScheduleExpression:.RestoreTestingPlan.ScheduleExpression,
    ScheduleExpressionTimezone:(.RestoreTestingPlan.ScheduleExpressionTimezone // "Etc/UTC"),
    StartWindowHours:.RestoreTestingPlan.StartWindowHours
  }
}' /tmp/naaseh-restore-plan-original.json > /tmp/naaseh-restore-plan-restore.json

aws backup update-restore-testing-plan \
  --profile "$AWS_PROFILE" --region "$AWS_REGION" \
  --cli-input-json file:///tmp/naaseh-restore-plan-restore.json

aws backup get-restore-testing-plan \
  --profile "$AWS_PROFILE" --region "$AWS_REGION" \
  --restore-testing-plan-name "$RESTORE_PLAN" \
  --query 'RestoreTestingPlan.{Schedule:ScheduleExpression,Timezone:ScheduleExpressionTimezone,StartWindowHours:StartWindowHours}'
```

The restored schedule must again be `cron(0 6 1 */3 ? *)`. Wait for both restore jobs to finish,
then rerun `list-restore-jobs`. DynamoDB must show `Status: COMPLETED`, `Validation: SUCCESSFUL`, and
successful deletion of the AWS Backup-managed temporary table. The deployed validator now calls
the Journal and Crisis Plan ciphertext validators and rejects invalid schemas, unauthorized owner
relationships, Journal key rollback, Crisis Plan key/share-generation rollback, grants on revoked
or removed shares, and stale recipient GSI entries. It never decrypts Journal or Crisis Plan data.

Finally confirm the restore workflow alarm is `OK`. If any job or validation fails, stop the
release, preserve the safe job/event identifiers, and follow
[Journal restore](../runbooks/journal-restore.md) and
[Crisis Plan operations](../runbooks/crisis-plan-operations.md). Do not manually delete an
AWS Backup-managed restore resource while its deletion state is pending. Delete only resources
confirmed to be operator-created and isolated.
