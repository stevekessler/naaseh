# Data Model — Contacts and Inventory

## Scope and partitioning

Feature-owned DynamoDB uses a server-derived workspace partition for contacts, inventory and image references, with mutation receipts scoped to the authenticated actor and workspace. Catalog values and admin receipts use separate keys. Contacts and inventory use stable application-generated UUIDs, created once even for an offline draft. Revisions and timestamps are server-controlled. The authenticated account must match one of the two configured workspace member IDs. Clients cannot set or change workspace membership. Use bounded workspace queries. Core tasks, Finance, and native synchronization have no feature records or schema migration.

## Records

| Entity | Fields and rules |
| --- | --- |
| Contact | UUID, workspace, revision, timestamps, prefix, first name, last name, phone, fax, cell, emergency number, default number field, address lines 1 and 2, city, state, zip, optional contact type ID. Require at least one nonblank name. New forms default state to `CO`. Persist postal codes and numbers as strings with display formatting preserved. The default selector is nullable and may point to a populated phone, cell, or emergency field. Clearing that number also clears the selector. |
| Contact Type | Stable ID, display label, revision. Seed one immutable identity for Prescriber. Renaming changes its label only. |
| Location | Stable ID, name, optional multiline details, revision. Trim the name, preserve internal line breaks in details. |
| Strength Unit | Stable ID, display label, revision. Idempotently seed `mg`, `G`, `mcg`, `oz`, `mL`, `IU`, `g/mL`. Preserve label case and IDs. |
| Inventory Item | UUID, workspace, revision, timestamps, item name, location ID, type discriminator `base` or `medicine`, active image ID and image generation. Require a nonblank name and an existing location. General user updates preserve the image slot. The type stays fixed after creation. |
| Medicine data | Fields on the Medicine item, including Who’s Med (`steve`, `heather`, `both`, `penny`, `otc`), Status (`current`, `discontinued`), Include on Med List (boolean, default false), optional strength number (finite decimal), optional strength unit ID, optional Other and Dose text, Time Taken (`morning`, `night`, `morning-and-night`, `prn`), optional expiration date and optional prescriber contact UUID. Store expiration as a validated `YYYY-MM-DD` calendar date. Who’s Med, Status and Time Taken are required. Base items reject Medicine fields. |
| Image candidate | UUID, owning item ID and workspace, staging object key and exact S3 version after upload, validated media type and size, scan state, expected image generation and processing timestamps. The active image is available only through the item’s active pointer. |
| Mutation receipt | Authenticated actor and workspace or authorized admin scope, mutation ID, operation/resource identity, canonical request digest and the recorded successful response metadata. Store atomically with state changes. Reusing a key with the same request replays the original result and never repeats side effects. Mismatched requests conflict. Keep receipts for the supported replay lifecycle, with no expiry in the first release. |
| Change entry | Workspace sequence, record kind and UUID only. Resolve the latest projection at read time. Each current record carries its last change sequence, including for image changes. Keep scalar revision and image generation separate for write preconditions. |
| Deletion ledger | Minimal workspace, kind, UUID, sequence, and revision or image generation, stored independently of the live table. Retain record deletions and active image invalidations across release rollback and restore. |
| Browser store | Account-bound encrypted records, references, outbox, and conflicts. Account ID and minimal queue counts are available for host lifecycle handling. Search projections are derived in memory and cleared on lock or account change. |

Use shared request validation with explicit max lengths for short inputs and long memos. Preserve internal whitespace and punctuation when meaningful. Use case-insensitive name matching and digits-only comparison for phone queries while preserving display strings. Scope any opaque pagination token to the account and collection.

## Reference integrity and edits

- Persist managed references by ID and resolve their latest labels. Catalog creation and relabeling are online admin actions with revision checks. Catalog deletion is outside the first release. Seed writes use stable IDs and preserve administrator-edited labels.
- Linking Medicine to a Prescriber requires the contact to be active in the same workspace and to have the built-in Prescriber type. Transactionally update a reference count when linking, clearing or changing the contact, with workspace, active-state and type predicates. A contact may change away from Prescriber only when that count is zero. Use conditional writes so simultaneous changes cannot orphan a link. Validate location/type/unit references at commit time. A user-facing scalar revision guards edits from multiple devices. Internal reference counters do not overwrite user fields or rewound drafts.
- Store a local record and pending mutation in one transaction. Replay account-scoped entries in dependency order, including an offline Prescriber creation before its Medicine link. Refresh paginated snapshots after replay and merge monotonically by revision so a stale fetch cannot replace recent local state. Clear a draft only after acknowledgment or explicit discard. Retain both local intent and current server state for a conflict and require an explicit resolution before retrying.

## Deletion and synchronization

- Either member can delete an active record with the current revision. Commit a tombstone and a receipt in the same transaction, clear and advance the image slot for inventory, and decrement any linked Prescriber count when deleting Medicine. Delete a referenced Prescriber only after all links are cleared or reassigned. Retain the tombstone so UUIDs cannot be reused.
- Write a metadata-only change entry atomically with each record or active-image change. Allocate the next workspace sequence with a conditional counter update in the same transaction. Page entries in sequence order using strongly consistent reads and resolve their IDs to current state. A later edit can appear early, so merge by the last change sequence and persist the applied page and cursor atomically. Bound catch-up by the server’s committed high-water mark for that pass. Refresh the small shared catalog on reconnect and after catalog edits. A snapshot captures a replay boundary before loading pages and catches up through the change feed. Tombstones suppress stale pages, drafts, uploads and replay responses. For a deleted record, purge its cached payload, search state and transient image. Keep a metadata-only failed operation for user feedback and remove the stale payload from the sendable queue.
- Write the deletion ledger entry in the same regional transaction as the tombstone or any image-slot update that invalidates a previous image. During restore, pause feature writes and image processing, capture the authoritative ledger watermark and reapply entries absent from the paired recovery points. Keep the feature offline if the ledger cannot be verified. Clear any restored image slot that would expose an invalidated image, then recompute reference counts. If a restored Medicine points to a deleted contact, clear that reference and surface the recovery outcome in protected operational notes. Advance the workspace sync generation and require a fresh snapshot before replay. Preserve eligible queued drafts for explicit reconciliation across the recovery boundary. Old upload candidates, scan events and unapplied writes from the earlier generation cannot commit.

## Image state and retention

1. An authenticated workspace member starts a candidate against the current image generation. Validate JPEG or PNG, sanitized filename, and size from 1 byte to 25 MiB. Upload directly to the authorized candidate object.
2. Verify actual type, size, and object version. Await the scan result for that exact version. Only a verified clean result can proceed, even if scan events arrive before the client confirms upload or arrive more than once.
3. Atomically activate one clean candidate and increment the image generation only when the item still has the expected generation. A losing, invalid, or timed-out candidate stays unavailable. A failed replacement leaves the existing image active. A removal clears the pointer and increments generation, so an earlier candidate cannot revive it.
4. Each authenticated bounded image read rechecks membership, active item state, and the current pointer, then returns bytes from the exact clean version without a reusable download URL. Reconcile stuck candidates and prune expired unreferenced staging objects according to the retention policy, retaining versions required by backups or restore.
5. Keep DynamoDB PITR and backup coverage, image bucket versioning and backup selection, and the encryption key across rollback. Record the restore-point pairing and verify restored links, workspace access, tombstones, pointer generation and clean object versions in an isolated destination before cutover. Release rollback keeps saved data. Destructive schema changes or backup purges require a separate reviewed lifecycle change.

## View projections

- Contacts filters combine name/number text and contact type. The Prescriber picker uses the same shared workspace directory and stable type identity.
- Inventory filters combine name, location, and type, with additional Medicine predicates as defined in the spec. Reset Medicine-only filters when switching to Base or All. The medication list only includes Medicine records with Include on Med List on.
- Combined Search uses three independent result scopes and existing obscured/private-data boundaries. Project minimal labels and stable detail links, exclude disabled types from counts and results, and avoid persisting queries or sensitive snippets in logs or preference storage.
