# Research — Contacts and Inventory

## Independent web release

- **Decision** — Add a narrow, backward-compatible host integration once from the supported Na’aseh baseline. It reserves the Lists, Inventory, Admin, and Combined Search slots and same-origin asset path for feature 017. Release the feature as separately built UI assets, API code, and feature-owned infrastructure and data. The first install plan includes the host preparation. Subsequent feature releases and rollbacks operate exclusively on the feature. Host releases, including Finance web releases, must preserve the versioned integration.
- **Rationale** — The current host hardcodes routes and menu items, builds one precached web shell, prunes the web asset bucket on deployment, and rolls back the entire app SHA. Evidence: [web app](../../apps/web/src/app/App.tsx), [router](../../apps/web/src/app/router.tsx), [PWA configuration](../../apps/web/vite.config.ts), [web infrastructure](../../infra/lib/web-stack.ts), and [AWS release runbook](../../docs/operations/release-with-aws.md). Give feature assets a private, separate bucket and a fixed CloudFront behavior for `/features/contacts-inventory/*`, with immutable versioned assets and an uncached release manifest. Static bundle URLs must remain same-origin. Restrict module loading to trusted writes to the feature bucket and the known namespace. Edge/cache policies are documented in [CloudFront cache behaviors](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/DownloadDistValuesCacheBehavior.html).
- **Alternatives considered** — A feature flag or separate Git branch with the current whole-app release couples application rollback. A standalone site or an iframe would require more integration for native shell routing, session, accessibility, offline behavior, and Combined Search. Runtime loading is limited to this feature’s typed integration.

## API and authorization

- **Decision** — Declare feature-owned REST-style routes on the existing HTTP API, under `/api/v1/contacts-inventory/`. Import stable API and session-authorizer IDs exposed by the baseline bootstrap. The existing default stage auto-deploys routes. Keep Lambda code and publishable versions under feature ownership. Authorize every route, validate CSRF for mutations, and resolve the authenticated principal against the two server-configured account IDs and derive the workspace key server-side. Administrative catalog writes require the existing admin role.
- **Rationale** — The current CloudFront API behavior disables caching and forwards the session cookie. The existing session authorizer handles revocation and supplies identity and CSRF context, with authorizer cache disabled. This retains the host’s security behavior and leaves existing Finance URLs and native sync wire formats intact. See [API stack](../../infra/lib/api-stack.ts) and [AWS HTTP API route resource](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-apigatewayv2-route.html).
- **Alternatives considered** — A second gateway adds routing and authorizer infrastructure. Adding inventory to the shared task sync or attachment APIs couples this feature to existing schemas and consumers. Repo libraries may be reused at build time. Runtime integration is through the explicit host contract.

## Records and offline search

- **Decision** — Use an on-demand DynamoDB table with one workspace partition for the two authorized members, point-in-time recovery and deletion protection. Keep catalogs in a separate partition in the same table. Use conditional revisions and transactional idempotency receipts. For the specified workload, fetch paginated workspace records and use a memory-only matching projection. Browser caching and mutation queues live in a separate feature IndexedDB database, encrypted under the existing device vault with user/account context.
- **Rationale** — The existing [outbox](../../apps/web/src/db/outbox.ts), [vault](../../apps/web/src/crypto/vault.ts), and [foreground refresh](../../apps/web/src/sync/foreground-sync.ts) provide patterns for atomic local writes and Safari reconnect. The feature has bounded workspace datasets and supports offline browse without a paid search service. Account change, lock, revocation and sign-out apply to the separate store, including pending-change warnings before confirmed sign-out. Paged reads merge monotonically with optimistic edits; persisted data and drafts are encrypted and the search projection is rebuilt in memory.
- **Alternatives considered** — Sharing the core table, sync cursor, or Dexie schema increases release and restore coupling. Provisioned search is unnecessary for the baseline workload. Server-only search loses offline parity.

## Image lifecycle and recovery

- **Decision** — Use a retained, encrypted and versioned feature media bucket. Reuse the task JPEG/PNG policy and workflow patterns at build time, with an image-specific allowlist, scoped short-lived presigned uploads and authenticated, bounded image reads and GuardDuty scan results on EventBridge. Publish a verified candidate by conditionally updating the item’s active image pointer against its expected generation. Register feature data and media for backups explicitly and restore them together into isolated destinations.
- **Rationale** — Task/list attachment authorization is tied to its own parent types. Existing task media shows how to quarantine and reconcile uploads. A separate generation avoids conflicts between ordinary item edits and image scans, and prevents a late scan or competing upload from replacing the active image. The exact media bucket origin is allowed in host CSP and the media bucket allows the exact web origin in CORS. See [task attachment policy](../../apps/api/src/attachments/file-policy.ts), [task attachment authorization](../../apps/api/src/attachments/attachment-authorization.ts), [media stack](../../infra/lib/media-stack.ts), [backup stack](../../infra/lib/backup-stack.ts), and [GuardDuty for S3](https://docs.aws.amazon.com/guardduty/latest/ug/gdu-malware-protection-s3.html).
- **Alternatives considered** — Reusing the task attachment routes would expand their authorization model and shared contracts. Overwriting a single object in place exposes the wrong bytes during replacement or failure. A retained pointer and versioned storage make deterministic rollback and recovery possible.

## Incremental AWS cost and observability

- **Decision** — Use existing regional infrastructure in `us-west-2` with HTTP API, Lambda, DynamoDB on demand, S3, GuardDuty, EventBridge, AWS Backup and CloudWatch. No new distribution, managed search cluster, provisioned capacity, or separate always-on service. Follow existing audit retention and controls. Use a feature key for retained media when the existing approved key cannot be scoped safely.
- **Planning envelope** — Model 1,000 contacts/items per active account, 100,000 billed read units and 20,000 billed write units across accounts per month, 20,000 API requests, a 256 MiB Lambda averaging 250 ms, 0.1 GB of DynamoDB data, 2 GB of retained images and 0.5 GB across 250 monthly image uploads. Search over memory-resident records adds no per-query cloud charge. Using AWS public example rates as planning inputs, approximate database reads/writes/storage at $0.05/month before PITR, API/Lambda at $0.05, image storage and scanning at $0.15 before backup, network and S3 requests. Allow $1–$5/month total as a planning range after key, log, alarm, backup and transfer overhead at this volume. Validate Oregon pricing, expected retention, rollback artifact storage and scan load against the actual deployment before release. Existing fixed platform costs are outside this incremental estimate. [DynamoDB](https://aws.amazon.com/dynamodb/pricing/) · [HTTP API](https://aws.amazon.com/api-gateway/pricing/) · [Lambda](https://aws.amazon.com/lambda/pricing/) · [S3](https://aws.amazon.com/s3/pricing/) · [GuardDuty](https://aws.amazon.com/guardduty/pricing/) · [CloudWatch](https://aws.amazon.com/cloudwatch/pricing/)
- **Rationale** — Retained image versions and backups, scan volume/object counts, cold snapshot reads, and alarms are the main variable or fixed cost drivers at this scale. Track storage growth, consumed units, request and replay p95, scan failures and scan age. Use 30-day application logs and 90-day protected audit logs aligned with [observability infrastructure](../../infra/lib/observability-stack.ts). Logs capture request correlation, operation, outcome and timing. Exclude record values, keys/presigned URLs, query strings, and raw bodies.
- **Alternatives considered** — Shared storage saves minor overhead but makes isolated restore and least privilege harder. Fewer retention copies can reduce storage only within the approved recovery policy. Revisit query shape or add a narrowly scoped projection only after measured load requires it.

## Shared workspace and deletion

- **Decision** — Resolve the two account IDs server-side and give both identical record read, edit and delete rights. Catalog authority remains separate. Deletion writes a durable tombstone with revision checks and clears the image pointer. Current reads exclude deleted records. The sync feed stores only change identifiers and ordering metadata, and resolves each identifier to its current active record or tombstone when serving a page. Use strongly consistent table reads so a committed deletion is visible to subsequent requests. Keep a minimal deletion ledger in a separate retained DynamoDB table and record tombstones and image invalidations in the same transaction as the corresponding live update. [DynamoDB read consistency](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadConsistency.html) · [DynamoDB transactions](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Constraints.html)
- **Rationale** — The workspace boundary gives both members one canonical record while preserving separate sessions and browser caches. Tombstones propagate deletions to clients without treating an incomplete page as evidence of deletion. Delete eligibility for referenced Prescribers follows FR-013 and FR-015. To make image access end on deletion, serve bounded authenticated reads that verify the current record and image version on every request, with uncached responses. Use at most 4 MiB of raw bytes per authenticated response so buffered base64 plus the Lambda response envelope fits the synchronous quota. Re-estimate the provisional monthly range if range traffic, ledger retention, or storage grows beyond the model. [Lambda quotas](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html) · [HTTP API quotas](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-quotas.html)
- **Alternatives considered** — Per-record grants and private records add an access model outside the requested workspace. Unexpired presigned download URLs bypass feature record checks after deletion. Physical removal alone cannot distinguish stale offline edits from new records.

## Release evidence

- **Decision** — Use fixture-driven local validation for install/upgrade/rollback sequencing and protected production acceptance for infrastructure behavior, using disconnected AWS restore destinations for recovery. Use supported Finance build and existing native contract/liveness probes as compatibility fixtures. Use the protected operational canary for any actual production release.
- **Rationale** — The [release runbook](../../docs/operations/release-with-aws.md) documents that the repo has no standing staging environment. Unit or local AWS mocks are useful for deterministic races and regressions but cannot prove CloudFront origin order, IAM integration, API Gateway stage changes, real scan events, or restoration.
- **Alternatives considered** — A production-only first drill would make rollback and recovery harder to validate safely. A permanent staging stack adds unnecessary standing cost.
