# Web Host and Release Contract

## Stable integration

The one-time host preparation is built from the supported baseline. It provides explicit route and navigation slots, one module loader, feature offline cache lifecycle, and stable CloudFront/API bindings. First-install evidence must use that prepared baseline without the pending Finance or Mac/iOS changes. Later Finance builds inherit the host integration without bundling the Contacts and Inventory artifacts.

| Surface | Host responsibility | Feature responsibility |
| --- | --- | --- |
| Lists → Contacts | Register navigation and `/lists/contacts` plus detail URLs when compatible feature is available. | Mount directory, form and filter using a host-provided DOM container. |
| Inventory | Register top-level `/inventory`, item details, and medication list. | Mount Inventory, filters, edit/image flows and medication list. |
| Admin | Show Contact Types, Locations and Strength Units for authorized administrators. | Mount catalog screens and enforce authority again in the API. |
| Combined Search | Own search input, sort/display shell and three opt-in preferences. Always default missing or reset preference fields to false. | Return only enabled and workspace-authorized results. Return stable IDs, labels and supported detail hrefs. Keep results synchronized with accepted edits and deletions and remove stale contributions on lock/unmount. |
| Identity and offline lifecycle | Supply scoped same-origin request and encrypted store adapters bound to the active user. Signal lock, unlock, reconnect, foreground, sign-out, revocation and account changes. Coordinate existing pending-change warnings and data purge, including when the feature entry is inactive. | Own encrypted feature data and outbox semantics. Abort in-flight operations and release in-memory data when host context changes. Return pending counts without exposing values. |
| Route fallback | On missing/incompatible release, hide feature entries and show a safe unavailable state for deep links. Keep existing pages, Search options and browser navigation usable. | Dispose all handlers, timers, mounts and search results on unmount. |

Host and module exchange a versioned TypeScript contract. Publish only the feature’s known contributions. The module has its own mount/render boundary, so host and module may build React separately. Pass no raw session cookie, device key or host data stores. The request adapter attaches the existing CSRF header for mutations, restricts calls to the selected same-origin feature API prefix, and uses the host’s same-origin session. The vault adapter binds feature and user identity in associated data. The host fetches only the configured manifest and accepts immutable same-origin artifact paths under the feature prefix. Protect bucket and manifest write permissions through deployment roles. No user input supplies executable URLs.

## Artifacts and routes

- `/features/contacts-inventory/release.json` is nonpersonal, fetched without cache while online, and served from a separate private static origin. Required properties are `releaseId`, `hostProtocol`, `apiProtocol`, `entry`, and `assets` (precachable immutable UI assets including the entry and its dependencies). An inactive release has no active manifest or returns an explicit inactive payload. Keep manifest URLs outside SPA rewrite and service worker navigation fallback.
- `/features/contacts-inventory/releases/{releaseId}/` serves immutable packaged UI assets. An already provisioned device can open a known compatible cached release offline using its saved manifest pointer and cached executable assets. Cache only public immutable feature artifacts in the worker. Private responses, signed URLs, manifests, and image bytes are excluded from service worker caching. A definitive inactive or incompatible response must not restore old UI online.
- `/api/v1/contacts-inventory/releases/{releaseId}/` is the feature API namespace. A feature-owned route/integration for each retained runnable release selects an immutable Lambda version or a release-pinned alias. Import the platform HTTP API and authorizer IDs. Keep API traffic uncached with HTTPS, the existing session flow, CSRF, and the same security headers.
- The artifact origin, private data and media resources are retained independently. Core asset pruning and Finance/native release workflows must have no ownership over feature versions, manifest publication, data table, or media.

## Deploy and rollback

1. Prepare durable feature destinations and one-time host bindings when absent. Proof before delivery must show that the prepared baseline behaves normally without the feature manifest. Once prepared, no host build or host configuration change is required for routine feature activation.
2. Produce immutable artifacts from the feature source SHA and a single release ID. Update the feature stack/API integration, apply only additive data changes, publish immutable UI assets, and probe both API authorization and asset loading. Leave the current release active during preparation.
3. Publish the active manifest last through the protected workflow. Verify live route and assets for the exact manifest version, then run canaries. Keep the previous runnable release and its artifacts supported through the rollback window. Mixed tabs and queued writes must be handled without destructive data-format changes. Every runnable release must understand current tombstones, enforce the same membership and image access checks, and honor sync generation resets.
4. On upgrade failure before publication, keep the current manifest pointer. On failure after publication, repoint the manifest to the verified prior release or mark inactive for first-install rollback. Block requests to the withdrawn release or have them return an explicit unavailable response. Recheck the manifest on foreground or API rejection. Preserve editable drafts and do not replay blindly against an incompatible schema. Retry against a compatible release using the same mutation IDs.
5. Verify Finance build fingerprint, native endpoint behavior and feature data retention across transitions. Redeploy using retained data. Do not roll back a shared web/API release SHA as the feature rollback mechanism.
6. A browser tab offline at rollback can continue local work from its previously trusted cache until reconnect. Once online it must honor the manifest state. A later authorized redeployment can recover queued drafts for the same account. Sign-out and revocation rules continue to apply.
